# Venue Data Sheet

Master table of every venue in `universal_scraper.py`'s `VENUES` dict, plus venues we looked at and rejected. Companion to [ONBOARDING.md](ONBOARDING.md) (the process) — this file is the data. Update a venue's row whenever you dry-run or re-verify it (§6 of the onboarding playbook).

**Column meanings:**
- **Platform** — what the venue's page/calendar is built on (Prekindle, SpaceCraft, Etix, custom WordPress, Timely, SeeTickets, ICS feed, etc.)
- **Config** — non-default `VENUES` dict keys in use for this venue (beyond `name`/`url`/`city`/`state`/`wait_time`)
- **Events** — event count from the most recent dry-run or scrape
- **Date/Time Capture** — how reliably `start_date`/`start_time` came through clean
- **URL Capture** — how reliably `ticket_url`/`event_url` came through
- **Extra Fields** — anything beyond the basics this venue's page exposes and we capture (`doors_time`, `location`/room, multi-night ranges, `openers`, etc.)
- **Last Verified** — date of the stats in this row

Rows marked **"Not yet verified"** haven't been dry-run/re-checked during an onboarding session with this table in place — their config is accurate (read from source), but the data-quality columns are unconfirmed rather than guessed.

## Automated health dashboards (already exist — read before "reviewing" anything)

Two dashboards already track venue health automatically. Know what they cover before assuming a manual review is needed:

- **`/venue_health`** (review_dashboard.py, older) — per venue: upcoming/pending/canceled-in-30-days/new-in-7-days counts, plus a red/yellow/green flag driven by scrape recency (via `venue_cache.last_scraped`), cancellation spikes, and pending backlog size.
- **`/health`** (review_dashboard.py, newer "alternative" route) — per venue: a 12-week **new-events-per-week** trend chart (as of 2026-07-19; previously charted `total_scraped`, which double-counted already-seen duplicates re-detected on every run — `new_events` is the true per-run delta), `missing_time_pct`/`missing_url_pct` (% of approved events missing a start_time, or missing both `ticket_url` and `event_url`), and a good/warning/error flag combining staleness (>7 days since last scrape), duplicate counts, **and now new-event trend decline**: 0 new events for 1wk → warning, 0 for 3wk → error; a ≥50% drop over the last 6wk vs. the prior 6wk → warning, ≥75% → error (rate check only applies once the prior-6wk baseline is ≥6 events, to avoid noise like 2→1 registering as a "decline"). Whichever signal (staleness/duplicates vs. trend) is worse wins.
  - **Important caveat, by design**: the trend flag is a "worth a look" signal, not a diagnosis — a decline can mean the scraper broke just as easily as it can mean the venue genuinely booked fewer shows. Treat a flagged venue as a candidate for the manual review below, not a confirmed bug.
  - There was a second, near-identical copy of this route's logic sitting in an untracked, never-imported `health_route.py` file — dead code, not what the live app runs. Deleted 2026-07-19 to avoid future confusion (it very nearly got "fixed" instead of the real route).

**What neither dashboard checks:** whether the URLs in the `VENUES` config actually still resolve, still point at the right business, or point at the best available target. Both are entirely DB-derived — they can tell you a venue hasn't been scraped in 10 days, that half its events are missing a ticket link, or that its new-event rate has cratered, but they can't tell you `heightstheater.com` is a Minnesota movie theater, or that a scrape source 404s. That's what the manual review below is for. Run it periodically, or whenever something looks off in one of the automated dashboards (a `/health` trend flag or a spike in `missing_url_pct` are both good triggers).

## Manual venue health review

A periodic (not per-scrape) pass checking that each venue's configured URLs are actually correct — not just present. Prompted originally by a dead link surfacing in the review dashboard's event-edit popup; see the 2026-07-18 entry under Open Items for the first full pass.

**1. Check every configured URL actually resolves.**
```python
# curl each VENUES[key]['url'] (and ['venue_url'] if set) with a browser UA, check status
```
A 404, a DNS failure (`curl: (6) Could not resolve host`), or a WAF challenge page (200/202 with near-empty body) all count as broken — don't stop at "got a 200," some WAFs return 200 with a maintenance/challenge page instead of real content.

**2. Check the DB for multiple distinct `venue_url` (or `url`) values per venue name.**
```sql
SELECT venue, venue_url, COUNT(*) FROM events GROUP BY venue, venue_url ORDER BY venue;
```
More than one distinct value for the same venue name is a signal that the config changed at some point and old rows were never backfilled — `venue_url` is only set at insert time, never retroactively. Check each distinct value's status individually; don't assume the newest one is right or the oldest one is wrong without checking both.

**3. Before treating a same-name domain as "the venue's own site," confirm it actually is.** A 200 status isn't identity confirmation. Check the page's actual content — address, "About" text, branding — against the venue you think it is. (`heightstheater.com` returning 200 with a real-looking nav turned out to be an unrelated 1926 movie theater in Minnesota; the real Houston venue was at `theheightstheater.com`.)

**4. Check whether a venue's own domain is a thin redirect to a ticketing platform, and prefer it if so.** If the venue's own domain 302s straight to Prekindle/ATG/Etix/etc., link to the venue's own domain as `venue_url` rather than the raw ticketing-platform URL — one less layer of platform lock-in if they ever switch providers, and it reads better than a bare third-party link. Confirm the redirect actually happens (`curl -sL -o /dev/null -w '%{url_effective}'`); don't assume based on the domain name alone.

**5. Check for venues where the scrape path structurally can't set a field, not just where the data happens to be stale.** Venues on a custom code path (`scrape_timely_api`, `parse_seetickets_html`, `ajax_scrape`, `scrape_google_ics`) don't automatically get the same per-event field population as the generic LLM path — each of those functions builds its own event dict by hand. If a field is blank across *every* row for a venue (not just some), check whether the responsible function ever sets that field at all, rather than assuming it's a data quality issue to backfill and move on.

**6. Before touching the database, confirm scope with the user.** Present the specific rows/venues affected and the proposed before→after values; this is production data serving a live dashboard, not a local fixture.

**7. Update this file.** Record what changed, in the venue's row and/or under Open Items, with the date.

## Open items

- **Year-rollover bug** (bare `month/day` dates defaulting to current year instead of rolling to next year when already past) — seen on `secret_group`, likely affects any venue whose page omits an explicit year. Not fixed yet, per explicit decision to leave as-is for now.
- **Echoes HTX real source, under active observation (started 2026-07-26)** — their own site (not Facebook — ruled out) is the right source: they post event info directly on-site fairly regularly, but only for a short window, typically just the day of. Where exactly on the site it appears hasn't been pinned down yet — the `/event-calendar` page's Wix calendar widget was confirmed empty (both Month and Agenda views, and its underlying `calendar.apiboomtech.com` API returns 0 future events) and the homepage "Sounds" section read "No events at the moment" when checked, yet a real event was visibly posted somewhere on the site earlier the same day and was gone by the time it was checked again. Plan: check the site daily this week to catch it live and characterize where it appears and how long it stays up, before designing any scraping approach. The afternoon `schedule_group` cron (`--group afternoon`) is currently scraping the empty `/event-calendar` page and will keep no-op'ing until this is resolved.
- **Toyota Center** — needs a dedicated HTML parser like White Oak's before its ticket_url misattribution is fixed; DB intentionally empty until then.
- **This table's "Not yet verified" rows** — populate as each venue comes up for re-onboarding, a bug investigation, or a periodic health check; no need to do it in one pass.
- **`venue_url` audit (2026-07-18)** — prompted by a dead link surfacing in the review dashboard's edit popup. Two separate root causes found and fixed:
  1. `venue_url` gets baked into a row at insert time from whatever the config's `url`/`venue_url` was *then* — it's never backfilled on existing rows when the config later changes. Several venues had stale domains sitting in old rows from before a switch (Bad Astronaut, Heights Theater, Woodlands Pavilion, Riot Comedy, House of Blues) — all corrected in both `events` and `past_events`.
  2. `scrape_timely_api` and `parse_seetickets_html` (Continental Club/Big Top and Warehouse Live) never set `venue_url` at all — a code gap, not stale data. Fixed at the source; existing blank rows backfilled.
  - **Lesson for future onboarding**: when a venue's own domain looks right by name, verify it's actually still their site before using it — `heightstheater.com` turned out to be an unrelated 1926 movie theater in Minnesota, not the Houston music venue (`theheightstheater.com`, with "the," is correct). A same-name domain that returns 200 isn't enough confirmation on its own.
  - **Lesson on ticketing-platform indirection**: when a venue's own domain redirects to a ticketing platform (Smart Financial → ATG) rather than the venue lacking its own domain at all, prefer linking to the venue's own redirect page over the raw ticketing-platform URL — it's one less layer of platform lock-in if they ever switch providers, confirmed live via a real 302 redirect, not assumed.
- **New-event trend detection added to `/health` (2026-07-19)** — see the dashboard section above for the thresholds. Spot-checked against live data at launch: only 2 venues flagged (NRG Park, The Big Easy — both a genuine "0 new events this wk" after a real burst 10-12 days prior), 0 at error tier, confirming the logic isn't noisy out of the gate. Revisit thresholds if they turn out too loose/tight in practice — nothing about the specific numbers (1wk/3wk, 50%/75%, 6-event baseline floor) is load-bearing elsewhere, just tune in place.
- **`ticket_url`/`event_url` field misclassification (2026-07-21, in progress)** — the LLM extraction prompt (`extract_events_with_llm_raw`) asks for `ticket_url` and `event_url` as if they're always distinct, but many venues only have *one* link that genuinely serves both roles (a Ticketmaster page, or a venue's own event page that's also the buy-tickets destination). With no tie-breaking rule, the LLM's choice of which field to put that link in is unstable run to run — same correct URL, different field each time. Confirmed on `woodland_pavilion` (8 rows, 2026-07-19) and `house_of_blues` (23 rows, same day): in every case the URL matched exactly between the old and new row, just under a different column, so `save_to_database`'s URL-match (which only checks one field at a time) missed it and fell through to a `possible_duplicate` flag instead of updating in place.
  - **Not the same bug as Toyota Center.** Toyota Center's is a *positional* misattribution (a link gets attached to the wrong neighboring event, both being genuinely different shows) — actively dangerous to paper over with fuzzy matching. Cynthia Woods/House of Blues is a *labeling* problem on the *same, correct* event — safe to reconcile. Don't conflate the two when designing a fix; a cross-field check that would help the former would make the latter worse.
  - **Planned fix (three parts, prompt work starting now):** (1) pass the venue's own base domain into the extraction prompt plus an explicit rule — link on the venue's own domain → `event_url`; link to a known external ticketing platform (Ticketmaster, Prekindle, Etix, AXS, Square, Stubwire, SeeTickets, ATG) → `ticket_url` — so the labeling becomes deterministic instead of arbitrary. (2) A deterministic domain-based correction pass in code after extraction (near `scrape_venue`'s `event['venue_url'] = ...` line, the only other place we currently correct an LLM-produced field) — re-derive the correct field from the URL's domain rather than trusting whichever field the LLM chose, since prompting alone won't be 100% reliable. (3) Consolidate the scattered matching logic (`save_to_database`'s URL-match + name-floor, its separate partial-duplicate fuzzy check, and `check_canceled_events`'s independent fuzzy match) into one shared function scoring URL + name + date together, so future fixes to this logic only need to happen in one place.
  - **Considered and explicitly rejected as *the* fix: generic field-shape/type validation** (is `ticket_url` URL-shaped, does `start_date` parse). Reviewed against every real bug found this session — Cynthia Woods/House of Blues field-swap, Toyota Center's misattribution, the Riot Comedy Club domain-hallucination (see `urljoin` fix above), the year-inference bug — and in every case the LLM's output was syntactically valid, just semantically wrong (right shape, wrong field/event/year). Shape validation can't catch any of those. Worth keeping as a cheap supplementary layer regardless (it would catch genuine garbage, e.g. a `"Buy Now"` button-text string landing in `ticket_url` — 7 rows found DB-wide with exactly that value), but it's not a substitute for the domain-aware correction above.
- **LLM silently under-extracting a field, even when the source text plainly has it (noted 2026-07-23)** — found on both `armadillo_palace` and `numbers` during onboarding: the source page had clean, unambiguous "DOORS OPEN 7:00 PM" / "July 24 @ 9:00 PM"-style text for every event, and the LLM still returned `start_time: null` for all of them on the first pass. Neither the URL health-check process nor anything automated catches this — it was only caught because a human (who'd actually looked at the real site) noticed the dry-run output looked wrong. Decided **not** to add a `venue_instruction` to `armadillo_palace` to force-fix it: `save_to_database`'s URL-match/near-match update path (universal_scraper.py:1616-1690) will backfill `start_time` in place on a later scrape if extraction ever succeeds, without needing a manual DB fix — so a one-off under-extraction on a low-stakes field isn't worth preemptively engineering around per the usual minimal-`venue_instruction` rule.
  - **Revisit: turn `/health`'s `missing_time_pct`/`missing_url_pct` into an active signal, not just a static badge.** Right now these are computed per venue but only ever shown as a fixed `>30%`/`>50%` badge (health.html) — they don't feed into the venue's overall health color, and there's no history/trend on them the way the 2026-07-19 new-event-decline work added for `new_events`. Worth extending the same tiered-severity pattern (see that entry above) to these two metrics so a venue that's silently missing a field across most of its events gets flagged automatically instead of relying on someone noticing during onboarding, the way this one was.
- **LLM silently under-extracting whole events (not just a field) from a long, repetitive-shaped list — a third, currently-uncaught failure mode (2026-07-23)** — distinct from both entries above. `numbers`' combined 3-month calendar page repeatedly returned only ~8 of the true ~20 events; investigated in depth (see `pagination_sentinel`-era entries' method) and confirmed via direct `grep` that the actual model input had real duplication (page-boundary overlap between month views, `combined_text += page_text` with no dedup) and heavy repetition (one recurring weekly event's near-identical description block occurring 35 times across 3 pages) — not a raw character/token-limit truncation issue (total input was ~33k chars, well under the 100k cap). **Fixed at the source**, not papered over: added `header`/`nav`/`footer` to the tag-strip list in `scrape_page()` (previously only `script`/`style`) to cut the repeated site-chrome boilerplate that was diluting/duplicating the real content across concatenated pages — confirmed via A/B (raw `extract_events_with_llm_raw` calls on stripped vs. unstripped text) that this alone took `numbers` from ~8 events to the full ~19-20, end to end through the real pipeline (events *and* `event_url` both intact). Regression-tested against `improv_tx`, `shady_acres` (the two other paginated venues, same shared code path), `white_oak` (custom parser — confirmed untouched, since it reads the raw pre-strip `html` return value, not the stripped `soup`), and `house_of_blues` (see below) — no regressions found.
  - **However, while regression-testing `house_of_blues`, the same failure mode reappeared independently of this fix** — a production dry-run returned only 3 events (all same day) despite the page text clearly containing dozens (School of Rock, The Fixx, Rhythm & Reveal Revue, Julia Byers... visible directly in the extracted text). Direct A/B (stripped vs. unstripped, identical fetch) both returned a full, identical 36-event list when fed straight to `extract_events_with_llm_raw` — proving the header/nav/footer strip isn't the cause here either. The likely explanation: production's actual scrape (with its one configured scroll) pulled in more content than the quick single-snapshot test did, and at that higher event density the model returned **syntactically valid JSON with an incomplete event list** — no `JSONDecodeError`, so the existing split-and-retry safety net (`extract_events_with_llm_raw`'s `except json.JSONDecodeError` path) never engages, because it only catches literal JSON parse failures, not valid-but-truncated results.
